## 0. How to read this plan

Every task is **one TDD cycle and one commit**: the named failing test first, then the code that makes it pass. A dying builder loses uncommitted work (`.memory/builder-agents-must-commit-per-task`), so **every task below leaves the tree importing, collecting and green on its own** — commit before starting the next one, verify with `git show --stat`, no batching. Four tasks are deliberately larger than their neighbours because their halves cannot be green apart; each row says so and says why.

Order: schema → the pure resolver → repositories → the roster service → the floor cutover → routes+walkers → frontend wire → copy → components → e2e. The copy deck lands before the components so every component test asserts real Hebrew rather than a key echo, which is F39's shipped ordering.

Spec C1–C6 / D1–D17 and design F-1…F-33 / P1–P18 are binding and not restated. Everything in §1 was verified against `main` @ `11b1e8e` on 2026-08-10.

### 0.1 Three places this plan RESOLVES a spec ↔ design conflict, so the builder has no decision left

- **The assignment route answers `200` on both paths, not the spec's `201`.** Design F-2 turns it into an UPSERT on the live `(roster, template, staffer)` triple; a route that is sometimes a create and sometimes an update, answering two codes, forces the client to branch on a status to decide what it just did. One code, one client path. The spec's `201` row is superseded here and `test_shifts_api.py` asserts `200` for the create and the update alike.
- **Both assignment routes return the affected `RosterShift`, never the whole `RosterWeek`.** A whole-week payload per tap is the obvious shape and it breaks under §2.0's *deliberate* per-control concurrency: two writes in flight from one dialog, the earlier-issued response arriving second, and the pane silently loses the later assignment. See **F-A** in §5 for the client-side guard that makes even the per-shift shape safe, and R-C.
- **`edited_since_publish` and publish's no-op predicate are ONE repository method, computed once.** D7 needs "has the assignment set moved since `published_at`" twice — for the header line and to decide whether publish writes anything. Two implementations of that predicate is two answers to one question; `RosterAssignmentsRepository.changed_since(session, tenant_id, roster_id, since)` is the single source, and it counts **soft-deleted rows too** (a removal is an edit).
