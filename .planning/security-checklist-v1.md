The real answers are the cross-tenant key, a ceiling sized for shared egress, and an operator-visible signal that is not a response body. `config.py:82-85` reasons about the ceiling and not at all about the silence.

- [x] **`R28`** CSP forbids card fields / third-party scripts on our origin — **GREEN, closed by F21.**
  - A settings-derived `Content-Security-Policy` is built at `create_app()` time (`security_headers.py::build_csp`, wired at `main.py:704`) — never a module constant, because the media origin is a deployment fact. Ten directives; `script-src 'self'`; `style-src` carries **no `'unsafe-inline'`**; `frame-ancestors 'none'`; `base-uri 'none'`; `object-src 'none'`; `form-action 'self'`.
  - `media_csp_origin` reduces the bucket to scheme + netloc. Path-style addressing (`storage/s3.py:73-78`) is why the bucket name never appears in the host. **A deployment with no bucket gets a strictly tighter policy, never a broken one**, and `test_security_headers.py::test_the_csp_omits_the_media_origin_when_no_bucket_is_configured` is the test that says so.
  - **⚠ Both media settings were spliced into the policy unvalidated** (2026-08-05 review). A CSP is a `;`-delimited list and the browser honours the **first** occurrence of a directive, so `MEDIA_REGION="x; frame-ancestors *"` emitted `frame-ancestors *` ahead of this module's own `frame-ancestors 'none'` and turned clickjacking back on; `https://*` wildcarded `connect-src`. `MEDIA_ENDPOINT_URL` was already boot-blocked in production and forced `https://` outside dev — and `"https://x.test; frame-ancestors *"` satisfies both — while `MEDIA_REGION` had no check beyond non-empty. Six injection shapes and the invariant itself are pinned in `test_security_headers.py`. (`\r\n` was never a header injection: `urlsplit` drops it.)

- [x] **`R33`** Security headers: HSTS, CSP, X-Frame-Options, X-Content-Type-Options — **GREEN, closed by F21.** All four now ship.
  - **HSTS** is scheme-gated: `Strict-Transport-Security: max-age=31536000; includeSubDomains` is emitted only when the effective scheme is https, reading the **last** `x-forwarded-proto` entry. **No `preload`** — submission is effectively irreversible and belongs to a domain that resolves. `test_security_headers.py::test_hsts_is_emitted_over_https`, `::test_hsts_is_absent_over_http`, `::test_hsts_honours_the_last_forwarded_proto_entry`, `::test_hsts_carries_no_preload`, `::test_hsts_reaches_the_tenant_not_found_404`.
  - **Why `x-forwarded-proto` is read unguarded while `x-forwarded-for` is not**: a spoofed XFF poisons a rate-limit bucket — a real attack. A spoofed XFP over plain HTTP makes the app emit a header the browser **ignores by specification**. Nothing to spend, nothing to poison; so one scheme condition replaces a config flag.
  - **`X-Frame-Options: DENY` and `X-Content-Type-Options: nosniff`** ship in `SECURITY_HEADERS` (`security_headers.py:60-66`).
  - **Neither new header joined `SECURITY_HEADERS`, and that is structural**: seven test modules compare that dict with `==`, which is only meaningful for headers that are unconditional and constant. The CSP is settings-derived and HSTS is request-derived, so both are emitted **beside** the dict by the same middleware. `::test_the_security_headers_dict_is_unchanged` is the guard against a later author "tidying" them in.
  - The middleware is registered **last** in `create_app()` and is therefore **outermost** (`main.py:704`), which is what puts it outside `TenantResolutionMiddleware` and gets the headers onto the `404 TENANT_NOT_FOUND` that middleware returns without reaching a handler — on a public storefront, the single most-served response to anyone probing the domain.

Against the pinned `pnpm@10.34.5` on a scratch project with `lodash@4.17.20` (5 advisories, 2 high, `pnpm audit` exit 1), **nine** settings each take that exit code to 0 — `pnpm.auditConfig.ignoreGhsas` and **`ignoreCves`** in `package.json`; the same two under a top-level `auditConfig` in **`pnpm-workspace.yaml`**; a severity floor via **`audit-level=` in `.npmrc`** or **`auditLevel:` in `pnpm-workspace.yaml`**; and — found by the round-2 review, in the very file the round-1 fix had hardened — **`ignoreUnfixable: true`**, **`ignore: [<id>]`** and **`fix: true`** in `pnpm-workspace.yaml`, which carry no audit-shaped name at all and return `{exitCode: 0}` (`dist/pnpm.cjs:148535`, `:148553`) before the advisory count is consulted. All nine were reproduced against the shipped binary. The rule is unchanged — an advisory may be silenced **only by id, only in `frontend/package.json`, and only with a rationale row that expires** — but the MECHANISM changed, because a nine-entry ban list would have been the same defect as the six-entry one. `package.json`'s lever surface is enumerable (pnpm `pick()`s a fixed key list out of `manifest.pnpm`, `dist/pnpm.cjs:18286`), so a ban list is honest there. `pnpm-workspace.yaml` gets **no key filter at all** (`:18322`, called at `:19096`): every key in it reaches the audit's options, so its lever surface is whatever pnpm's option set happens to contain. That file is therefore **allowlisted** — seven keys that configure what is installed and where, and anything else reds with "teach this script about it before using it", which is the posture `auditConfig` already had. Ruled out by the same experiment and recorded so nobody re-tests them: `pnpm.auditLevel`, a top-level `auditLevel` in `package.json`, a camelCase `auditLevel=` in `.npmrc`, and `ignoreRegistryErrors`/`prod`/`dev`/`json` in `pnpm-workspace.yaml` are all inert.
  - **And the guard now tests itself on every run.** `selfTest()` drives one leg per LINE of the checker — the nine levers, the two package.json shape checks, and each of the nine waiver-row checks — plus three clean controls, and throws before the real check runs. **Each leg asserts the MESSAGE it expects, not merely that something reded**, and that is the round-2 fix rather than a flourish: with a bare non-empty assertion, four lines were mutation-invisible. `added > today` and the 90-days-from-today cap mutually masked on the single fixture `{"added":"2099-01-01","expires":"2099-01-05"}`; the real-calendar-day round trip was masked because its fixture `2026-02-30` rolls to a date already in the past, so the leg reded on expiry instead (it is now `2026-09-31`, which rolls forward); and the two `package.json` checks had no leg at all. **Verified by deleting each of the sixteen guard lines in turn and re-running: all sixteen red.** Some masking is arithmetic and cannot be fixtured away — an expiry more than 90 days out implies a span over 90 days unless `added` is in the future — which is exactly why the assertion names the message.
  - **The property this buys, stated no wider than it is true:** unrecognised audit-relevant configuration in `package.json`, `pnpm-workspace.yaml` and `.npmrc` **fails closed**, and the command CI already runs is the regression test that it still does. That is stronger than an enumeration of today's levers, because it covers keys pnpm has not shipped yet. It is **not** a claim that no bypass exists anywhere: `npm_config_audit_level=critical` and `NPM_CONFIG_AUDIT_LEVEL=critical` both take `pnpm audit` to exit 0 and live in no file this guard reads. That lever needs an `env:` block in `ci.yml`, so it is guarded where workflow shape is guarded — `test_ci_gates.py::test_the_audit_job_sets_no_audit_level_env` — and named in the script's own header so the enumeration is not read as complete.
  - `--ignore-registry-errors` is **deliberately absent**: it would turn every registry outage into a silent pass, the same defect as `continue-on-error` under another name. Retry instead.
