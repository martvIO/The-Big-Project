# Spec: Feature 8 — Catalog Management (Epic E2)

**Created**: 2026-07-24 · **Revised**: 2026-07-24 (rev 2 — post six-critic verification pass) · **Status**: approved-for-build · **Epic**: E2 Feature 8 · **Effort**: M
**Depends on**: E1 #2 (media bucket provisioned; AWS account `not-started` — see Risks), E1 #5 (owner auth), E2 #7 (manage console shell + `/manage` router, CSRF middleware, error handlers) — branches off `main` · **Feeds**: E2 #10 (storefront catalog grid + dress detail read this shape), E2 #9 (design restyle must be amended to cover the new Catalog tab — see Risks 6), E5 #7 (date-bound reservation supersedes the manual `reserved` flag)

## Problem

F7 turned a provisioned boutique into a configured business, but the storefront has nothing to show. The E2 success criterion "customers browse the catalog and dress pages" and the storefront designs (`storefront-catalog.md`, `storefront-dress-detail.md`) were both drawn against a dress/variant/media shape that does not exist yet — the catalog grid, the price-visibility treatment, the "הוזמן" badge, the gallery, the size chips and the no-photo monogram state are all rendering data F8 must define. Nothing about photography can be faked: a bridal storefront without images is not a storefront, and image upload is the one part of this feature that touches infrastructure we do not own yet (the AWS account is `not-started`). The feature must therefore be buildable, mergeable and CI-verifiable **today**, with the production bucket reduced to configuration.

## Goal

The owner opens `{slug}…/manage` → **קטלוג**, creates a dress (name, description, price, price visibility, manual "הוזמן" flag, catalog order), sets its size/quantity matrix from a standard EU bridal quick-entry list plus free-text custom sizes, uploads up to 12 photos straight from the browser to S3 via a presigned POST policy, orders the gallery, and archives (and un-archives) dresses. "Out of stock" is never typed by anyone — it is derived from the variant rows. With no bucket configured the whole catalog stays usable: only the media write endpoints answer `503 MEDIA_NOT_CONFIGURED`.

## Design

### Data (migration `0006_catalog.py`, copying `0005_boutique_settings.py`'s structure: `_STANDARD` columns — which already include `tenant_id` — `_updated_at_trigger`, per-table `GRANT` + `enable_tenant_rls` loop)

`revision = "0006"`, `down_revision = "0005"`. `_STANDARD` and `_updated_at_trigger` are **re-declared locally** in `0006_catalog.py` — migrations stay self-contained; only `enable_tenant_rls` is imported from `app.db.rls`, exactly as 0005 does. `downgrade()` drops `dress_media`, `dress_variants`, `dresses` in that order.

All three tables are tenant-scoped, so `test_every_tenant_id_table_has_forced_rls` picks up FORCE RLS automatically. No foreign keys (house rule — `dress_id` integrity is app-level), TEXT not VARCHAR, TIMESTAMPTZ, soft delete, `uuid_generate_v4()` as the column default, money in integer agorot.

**CHECK-vs-constant rule (uniform, stated once).** Every numeric DB CHECK carries the lower bound plus an **absurdity ceiling fixed at exactly 10× the service constant** — INT4 headroom, so tightening product policy never needs a migration. `app/catalog/validation.py` carries the real cap. One deliberate exception: `dress_media.byte_size`, whose ceiling is 2× because the value is also a security bound the POST policy enforces. Where the bound is a *security boundary* rather than a product bound (accepted content types, media status), the DB pins the exact set. Each constant in the constants table below names its DB counterpart, so the pair is reviewable in one place.

- **`dresses`** — `name TEXT NOT NULL`, `description TEXT` (nullable), `price_agorot INTEGER CHECK (price_agorot IS NULL OR (price_agorot > 0 AND price_agorot <= 1000000000))` (nullable = "no price recorded"; 10× `MAX_PRICE_AGOROT`; money integer agorot, never float), `price_visible BOOLEAN NOT NULL DEFAULT true` (the §2 per-item visibility toggle; storefront renders "מחיר בתיאום" when false *or* when price is null), `reserved BOOLEAN NOT NULL DEFAULT false` (the manual, **date-less** owner flag — Hebrew "הוזמן"), `sort_order INTEGER NOT NULL DEFAULT 0`.
  Indexes: `idx_dresses_tenant_active ON dresses (tenant_id, sort_order, created_at DESC, id) WHERE deleted_at IS NULL` — the four keys fully cover the documented list order `sort_order ASC, created_at DESC, id ASC`, so paging is stable under concurrent inserts; `idx_dresses_tenant_archived ON dresses (tenant_id, sort_order, created_at DESC, id) WHERE deleted_at IS NOT NULL` (the archive view + restore, same ordering). Updated_at trigger. **No unique index on `(tenant_id, name)`** — boutiques legitimately carry the same designer model in two colours, and unlike `appointment_types` (which the booking UI picks by name) a dress is only ever addressed by id, so a duplicate name is a cosmetic annoyance, not a data-integrity hazard. The manage UI shows a non-blocking hint when a name already exists; the DB does not refuse the write.
- **`dress_variants`** — `dress_id UUID NOT NULL`, `size_label TEXT NOT NULL`, `quantity INTEGER NOT NULL DEFAULT 0 CHECK (quantity >= 0 AND quantity <= 10000)` (10× `MAX_VARIANT_QUANTITY`), `sort_order INTEGER NOT NULL DEFAULT 0`.
  Indexes: `idx_dress_variants_dress_active ON dress_variants (tenant_id, dress_id, sort_order) WHERE deleted_at IS NULL`; partial unique `idx_dress_variants_dress_size_unique ON dress_variants (tenant_id, dress_id, lower(size_label)) WHERE deleted_at IS NULL`. **`lower()` in the index, not the raw label**: the service normalises (strip, collapse internal whitespace) before writing, but that still lets `"US 6"` and `"us 6"` coexist as two stock buckets for one physical size. Hebrew has no case, so `lower()` is a no-op for the common path and a real guard for the Latin custom labels. Updated_at trigger.
- **`dress_media`** — `dress_id UUID NOT NULL`, `storage_key TEXT NOT NULL`, `content_type TEXT NOT NULL CHECK (content_type IN ('image/jpeg','image/png','image/webp'))`, `byte_size INTEGER NOT NULL CHECK (byte_size > 0 AND byte_size <= 20971520)`, `status TEXT NOT NULL DEFAULT 'pending' CHECK (status IN ('pending','ready'))`, `sort_order INTEGER NOT NULL DEFAULT 0`.
  The content-type CHECK is deliberate DB enforcement, not duplication: the accepted set is a **security boundary** (an `image/svg+xml` object served from our bucket is stored XSS on the storefront), so widening it must be a deliberate migration, exactly as 0005 made the refund bounds structural. The 20 MiB `byte_size` ceiling is the 2× absurdity guard; the real 10 MiB limit lives in `validation.py` and in the POST policy.
  `media_id` is **minted client-side in Python** (`media_id = uuid.uuid4()`) and passed as the explicit `id` on the INSERT, so `build_media_key(tenant_id, dress_id, media_id, content_type)` is computable *before* the row is written and `storage_key` is populated in the same, only statement. `uuid_generate_v4()` remains the column DEFAULT for any non-service writer. This follows the house precedent in `.memory/patterns/atomic-parent-child-across-rls.md`. There is no post-insert UPDATE of `storage_key`, and `storage_key` is never mutated after creation.
  Indexes: `idx_dress_media_dress_ready ON dress_media (tenant_id, dress_id, sort_order, id) WHERE deleted_at IS NULL AND status = 'ready'` (the gallery read path — the only one F10 will touch); `idx_dress_media_pending ON dress_media (tenant_id, dress_id, created_at) WHERE deleted_at IS NULL AND status = 'pending'` (the per-dress stale-pending sweep inside the presign transaction — tenant-first like every other index here, so one tenant's sweep never costs anything proportional to platform-wide upload traffic); plain unique `idx_dress_media_storage_key_unique ON dress_media (tenant_id, storage_key)` — **a regression guard on the key builder, nothing more**: because the key embeds the row's own PK it can only collide if `build_media_key` is ever changed to drop `media_id`, and this index turns that into an `IntegrityError` in CI rather than two rows pointing at one object. It contributes nothing to confirm idempotency (confirm is an UPDATE, never an INSERT). Updated_at trigger.
- **Grants + RLS** — the 0005 loop verbatim for all three tables: `GRANT SELECT, INSERT, UPDATE, DELETE ON {table} TO app_user` then `enable_tenant_rls(table)`. Nothing here is append-only, so no `REVOKE` dance (that pattern belongs to `terms_versions` / `platform_audit_log`).
- **ORM** — `app/models/dress.py`, `app/models/dress_variant.py`, `app/models/dress_media.py` extending `StandardColumns, Base`; `DressMediaStatus` StrEnum (`PENDING = "pending"`, `READY = "ready"`) added to `app/models/constants.py`. Repositories `app/db/repositories/dresses.py`, `dress_variants.py`, `dress_media.py` follow `appointment_types.py` exactly (RLS + redundant explicit `tenant_id` predicate, `soft_delete` returning a bool, `refresh` after flush to pick up the trigger-maintained `updated_at`). `DressMediaRepository.insert_pending(session, *, tenant_id, dress_id, media_id, storage_key, content_type, byte_size)` takes `media_id` and `storage_key` as required arguments.
- **No stored dimensions** — F8 does no image processing, so width/height would have to come from the client, and a client-reported dimension is a lie we would then render layouts against. The storefront's fixed 3:4 crop (`storefront-catalog.md`) is CSS; nothing needs the real pixels. Likewise no `alt` column: the passed design gate fixes alt text as "alt from the dress name" (`screens/design-system/README.md`).

### Derived status semantics

`out_of_stock` is **computed, never stored**: `total_quantity == 0` over the dress's non-deleted variant rows (equivalent to `not any(quantity > 0)` given the `quantity >= 0` CHECK) — so **zero variants ⇒ `out_of_stock = true`**. `CatalogService._stock_summary` is the single formula; it is fed by a pre-aggregated row for lists and by loaded rows for the detail, never by a per-row query. It is serialised onto `DressResponse` alongside `total_quantity` and `variant_count`. Nothing is stored because the only writer of stock is the variant-matrix replace, which rewrites the entire set in one transaction — a cached boolean would need either a trigger (invisible business logic in SQL) or a second write that can fail independently, and both create a state where the badge and the stock disagree. The variant rows are the single source of truth. **`out_of_stock` is a manage-only signal**: F10 does not consume it (see "Note for F10 (media + stock)").

`reserved` is stored, manual, boolean and **date-less**, and it is **independent of stock**: F8 exposes `out_of_stock: bool` + `reserved: bool` and **no single `status` string**, because the epic's three states are not mutually exclusive (a reserved dress can still have stock; an out-of-stock dress is usually not reserved) and collapsing them into one enum forces a precedence rule that neither storefront screen has. `storefront-catalog.md` shows "הוזמן" as a badge and `storefront-dress-detail.md` keeps the booking CTA live for a reserved dress — both are boolean reads, not an enum switch. `archived` (= `deleted_at IS NOT NULL`) is the third, orthogonal flag and is never returned to the storefront at all.

### Named constants (`app/catalog/validation.py`, mirrored in `frontend/apps/manage/src/validation.ts`)

These three bounds — and only these — live **once** here and are mirrored to the frontend. They are deliberately **not** env-tunable: `Settings` carries deployment identity (bucket, region, endpoint), never product policy. The DB CHECK is the absurdity ceiling above each, per the rule stated in Data.

| Constant | Value | DB counterpart | Why this number |
|---|---|---|---|
| `MAX_DRESS_NAME_LENGTH` | 200 | — | matches `MAX_APPOINTMENT_TYPE_NAME_LENGTH` |
| `MAX_DRESS_DESCRIPTION_LENGTH` | 4000 | — | 2× the profile description; a dress story is longer than a boutique blurb, still one screen of Hebrew |
| `MAX_PRICE_AGOROT` | 100_000_000 | `price_agorot <= 1000000000` (10×) | 1,000,000 ₪ — same sanity cap as `MAX_DEPOSIT_AMOUNT_AGOROT` |
| `MAX_VARIANTS_PER_DRESS` | 60 | — (list length capped in the request schema) | EU 32–58 even = 14 rows, ×4 headroom for custom labels |
| `MAX_SIZE_LABEL_LENGTH` | 32 | — | fits "מידה מיוחדת לפי מדידה" and "US 6 / EU 36" |
| `MAX_VARIANT_QUANTITY` | 1000 | `quantity <= 10000` (10×) | a boutique holds units, not pallets |
| `MAX_MEDIA_PER_DRESS` | 12 | — | 12 covers front/back/detail/train/veil variants with room to spare; each is an unprocessed ≤10 MiB original, so the per-dress worst case is 120 MiB of egress on a detail page |

| `MIN_UPLOAD_BYTES` | 1024 (1 KiB) | `byte_size > 0` | lower bound on the declared size; kills empty/probe uploads |
| `ACCEPTED_CONTENT_TYPES` | `{"image/jpeg": ".jpg", "image/png": ".png", "image/webp": ".webp"}` | `content_type IN (…)` (exact set — security boundary) | the extension map is server-side and authoritative — the key extension is derived from the declared type, never from the client filename. **HEIC excluded** (no browser renders it; Safari transcodes on pick), **GIF and SVG excluded** (SVG is executable markup) |
| `MAGIC_PREFIXES` | jpeg `FF D8 FF` · png `89 50 4E 47 0D 0A 1A 0A` · webp `RIFF` + `WEBP` at offset 8 | — | asserted at confirm against the object's first 16 bytes |

| `PENDING_MEDIA_TTL_SECONDS` | 3600 | — | a `pending` row older than an hour is an abandoned upload; it stops counting toward the cap and is swept. Injectable on `CatalogService` (see Testing) |
| `DRESS_LIST_DEFAULT_LIMIT` / `DRESS_LIST_MAX_LIMIT` | 24 / 100 | — | the manage list is the heaviest egress path in v1 — each row carries an unprocessed cover, so 24 rows is already ~240 MiB worst case. Raise it only once thumbnails exist |

`EU_SIZE_QUICK_LIST` (`32,34,36,38,40,42,44,46,48,50,52,54,56,58`, binding decision #2) is **frontend-only**, in `validation.ts`. The backend accepts free-text labels and has no consumer for the list; defining it server-side too would guarantee the two copies diverge.

Presign throttle bounds are **`Settings` fields**, not constants — every other rate limit in this codebase (`login_max_attempts`, `terms_creation_max_per_window`) is env-tunable so it can be adjusted during an incident without a code deploy: `media_presign_max_per_window: int = 60`, `media_presign_window_seconds: int = 300`.

### Storage port (`app/storage/`)

```python
@dataclasses.dataclass(frozen=True)
class PresignedPost:
    url: str
    fields: dict[str, str]

@dataclasses.dataclass(frozen=True)
class ObjectHead:
    content_type: str
    byte_size: int

class MediaStorage(Protocol):
    @property
    def is_configured(self) -> bool: ...
    def presigned_post(self, *, key: str, content_type: str,
                       exact_bytes: int, expires_in: int) -> PresignedPost: ...
    def signed_get_url(self, *, key: str, content_type: str,
                       filename: str, expires_in: int) -> str: ...
    async def head_object(self, *, key: str) -> ObjectHead | None: ...
    async def read_prefix(self, *, key: str, length: int) -> bytes: ...
    async def delete_object(self, *, key: str) -> None: ...
```

**Sync vs async, and why**: `presigned_post` and `signed_get_url` are pure local HMAC computation in botocore — zero network I/O — so they are plain `def`. Making them `async` would be a lie that costs an `await` per gallery item on every list response. `head_object`, `read_prefix` and `delete_object` are real network calls and boto3 is blocking, so they are `async def` on the Protocol and `S3MediaStorage` wraps the blocking client call in `anyio.to_thread.run_sync` (anyio already ships under Starlette — no new dependency) so the event loop is never parked on S3.

**Failure contract — the only place botocore exceptions exist.** Every `S3MediaStorage` network method wraps `botocore.exceptions.ClientError` / `BotoCoreError` and re-raises `MediaStorageUnavailableError`, carrying **no AWS-supplied text** (the original is logged with `tenant_id`/`dress_id`/`media_id`/`storage_key`, never returned). `head_object` returns `None` **only** for a genuine 404 / `NoSuchKey` head miss; a 500/503 from S3, an expired credential, a connect or read timeout is `MediaStorageUnavailableError`, never a silent "your upload never arrived". `NoCredentialsError` / `PartialCredentialsError` on any path map to `MediaNotConfiguredError` — a bucket without usable credentials is operationally identical to no bucket and must degrade the same way rather than 500.

Implementations: **`S3MediaStorage`** (boto3 client pinned to `signature_version="s3v4"`, region + optional endpoint from settings) and **`UnconfiguredMediaStorage`** (`is_configured = False`; every method raises `MediaNotConfiguredError`). The unconfigured object is chosen over `None` so no call site grows a null check and no code path can forget one. Tests use a third implementation, `InMemoryMediaStorage`. **`S3MediaStorage.__init__` performs no network I/O and no credential resolution** — it only builds the botocore client — so `create_app()` stays safe to call in the fast suite regardless of local `.env` contents. The instance is built once in `create_app()` and hung on `app.state.media_storage`; `app/catalog/router.py` defines `def get_media_storage(request: Request) -> MediaStorage: return request.app.state.media_storage` (mirroring `get_boutique_service`), and fast tests substitute via `app.dependency_overrides[get_media_storage]`.

**Credentials are bearer material.** `PresignedPost.fields` (which carries `policy` + `x-amz-signature`, valid 300 s) and any signed GET URL (valid 900 s) are never logged, never included in an error message, and any future request/response-logging middleware must redact `/manage/dresses/*/media/*` bodies. `Cache-Control: no-store` is set on the **router**, not per route, so a signed URL cannot land in a shared cache or a bfcache entry: nine of the eleven catalog endpoints answer with a `DressResponse` or `DressDetailResponse` carrying `cover.url` / `media[].url`, a tenth returns the POST policy itself, and enumerating them by hand is how six of them get missed. The one route with nothing to protect (archive → `OkResponse`) pays nothing for carrying the header, and a route added later cannot forget it.

**Config** (new `Settings` fields; names recorded in `.env.example`): `MEDIA_BUCKET` (`str | None = None` — presence is what `is_configured` means), `MEDIA_REGION` (`"il-central-1"`), `MEDIA_ENDPOINT_URL` (`str | None` — MinIO in CI, and a seam for any S3-compatible provider), `MEDIA_FORCE_PATH_STYLE` (`False`; MinIO needs `True`), `MEDIA_PRESIGN_MAX_PER_WINDOW`, `MEDIA_PRESIGN_WINDOW_SECONDS`. **AWS credentials are deliberately NOT settings fields** — `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN` are read by boto3's own provider chain from the process environment (Railway env only, per F2's B3), so they never enter our config object, never appear in a `repr`, and never get logged.

A `model_validator` **fails startup** when (a) `MEDIA_BUCKET` is set with an empty `MEDIA_REGION`, (b) `MEDIA_ENDPOINT_URL` is set while `app_env == "production"` — it is a CI/S3-compatible-provider seam and must be `None` against real AWS, (c) `MEDIA_ENDPOINT_URL` is set to a non-`https://` URL outside `dev`, or (d) `MEDIA_FORCE_PATH_STYLE` is `True` while `app_env == "production"`. **A missing bucket is never a boot failure** (binding decision #5) — but a *wrong* endpoint is, mirroring `_require_real_base_domain_outside_dev`.

Because `Settings.model_config` is `extra="ignore"`, a typo'd `MEDIA_BUKCET` is discarded silently. So the graceful degradation must be **observable**: `create_app()` logs one INFO line at wiring time — `media storage configured: bucket=%s region=%s endpoint=%s`, or `media storage NOT configured — upload endpoints will answer 503 MEDIA_NOT_CONFIGURED` — and `/health` gains `"media": "configured" | "unconfigured"` (never the bucket name), which is what F2's staging smoke checks before attempting the presign→upload→confirm→signed-GET run.

**Key scheme**: `tenants/{tenant_id}/dresses/{dress_id}/media/{media_id}{ext}`. Tenant prefix first satisfies the checklist's "S3 keys tenant-prefixed" and leaves room for a future IAM `s3:prefix` condition per tenant. `{ext}` comes from `ACCEPTED_CONTENT_TYPES`. The presign request body is exactly `{content_type, byte_size}` — there is **no field the client can send that influences the key**; `tenant_id` comes only from `get_current_tenant(request)` (host-derived) and `dress_id` only from a dress row this tenant actually owns (see Authorization invariants). `fields["key"]` necessarily exposes `tenant_id` to the browser: acceptable, because a tenant id is an identifier and not a secret, and no F8 endpoint accepts a tenant id from the client. The original filename is not stored at all in v1.

**Media origin isolation (standing invariant).** Media is served from an origin that is **never the tenant cookie domain nor any subdomain of it**. If a CDN or custom domain is ever placed in front of the bucket it must use a **separate registrable domain** — `media.<domain>` is same-*site* to the `{slug}.<domain>` session cookie, which is precisely the case `app/csrf.py`'s header comment documents as dangerous. This constraint is inherited by the deferred CDN work in Risk 3 and must be restated in that feature's spec.

**Not configured**: `presign`, `confirm` and `media delete` return `503 MEDIA_NOT_CONFIGURED` with the fixed body `{"error":{"code":"MEDIA_NOT_CONFIGURED","message":"Image uploads are not available."}}`. Everything else keeps working — dress CRUD, variants, reorder (a pure DB operation), and reads, where `MediaResponse.url` serialises as `null`. `DressDetailResponse.media_uploads_enabled` tells the UI up front (folded into the detail response rather than a separate `GET /manage/catalog/capabilities` — one fewer round-trip, one fewer endpoint to secure, and the UI still handles a 503 defensively in case config changes mid-session). No bucket, region, endpoint, env-var or IAM identifier appears in any user-facing message.

### Presigned POST policy

`generate_presigned_post` (POST policy, **not** PUT — binding decision #4: only a POST policy makes S3 itself enforce exact key **and** exact Content-Type **and** a length range). Conditions carried:

| Condition | Value | What it stops |
|---|---|---|
| `["eq", "$key", <server key>]` | the exact computed key | a client writing outside its tenant prefix, or over another dress's object |
| `["eq", "$Content-Type", <declared type>]` | one of the three accepted types | uploading an SVG/HTML payload under a jpeg presign |
| `["content-length-range", byte_size, byte_size]` | **the exact declared size** | zero-byte probes, bucket-filling, **and any object whose size differs from the row that authorised it** |
| `ExpiresIn` | `PRESIGN_TTL_SECONDS` = 300 | a leaked policy staying useful |

The length range is **exact, not `MIN…MAX`**. `MIN_UPLOAD_BYTES` / `MAX_UPLOAD_BYTES` remain the `validation.py` bounds on the *declared* value; pinning the policy to that declared value is what makes "declare 1 KiB, post 10 MiB" — a deliberate way to plant a large orphan the DB can never find again — structurally impossible. It also makes `MEDIA_MISMATCH`-on-size unreachable, leaving that code for content-type and magic-byte mismatches only.

**No `x-amz-server-side-encryption` condition or field.** Encryption is a **bucket property, not a form field the browser must remember to send**: S3 has applied SSE-S3 to every new object by default since January 2023, and pinning the header would additionally break MinIO (which rejects `x-amz-server-side-encryption` without a configured KMS) and every other S3-compatible target. **F2 §B3 requirement instead**: the bucket sets default encryption (SSE-S3) and a bucket policy `Deny s3:PutObject` when `s3:x-amz-server-side-encryption` is absent — see Risks 2.

**No `acl` field, deliberately**: the bucket is Block-Public-Access + Object Ownership "bucket owner enforced", where ACLs are disabled and sending an `acl` form field makes S3 reject the POST with `400 InvalidRequest`. Anyone tempted to "harden" this by adding `["eq", "$acl", "private"]` will break every upload.

Returned to the browser: `url` plus `fields` = `key`, `Content-Type`, `policy`, `x-amz-algorithm`, `x-amz-credential`, `x-amz-date`, `x-amz-signature`. The client posts `multipart/form-data` with **all fields first and `file` last** (S3 ignores anything after `file`).

**Read-side safety.** `signed_get_url` sets `ResponseContentType` to the stored `content_type` **and `ResponseContentDisposition=attachment; filename="{media_id}{ext}"`, not `inline`**. `Content-Disposition` is ignored for subresource loads, so `<img src>` still renders in the manage gallery and in F10's storefront; `attachment` only turns a *top-level navigation* to a signed URL from render into download — exactly the polyglot vector. Three layers guard content: the closed content-type allowlist pinned by the POST policy, this response override plus media-origin isolation, and the magic-byte assertion at confirm (below). S3 cannot emit `X-Content-Type-Options: nosniff` on a presigned GET (the override set is limited to response-content-type/-disposition/-encoding/-language/-cache-control/-expires), so these three are the whole defense and none of them is optional.

### API (`app/catalog/` module: `router.py`, `schemas.py`, `service.py`, `validation.py`, `keys.py`)

`APIRouter(prefix="/manage")`, registered in `create_app()` after the boutique router. Every route takes `Staff = Depends(get_current_staff)` + `get_current_tenant(request)`; every tenant-table access runs inside `tenant_session(session_factory, tenant.id)`. `CatalogService` is constructed in `create_app()` (session factory, `media_storage`, a `FixedWindowRateLimiter` built from the two presign settings with `clock=time.monotonic`, and `pending_ttl_seconds`), hung on `app.state.catalog_service`, and read by a `get_catalog_service(request)` dependency exactly as `get_boutique_service` does. FastAPI-idiomatic verbs, matching F7 (the Micronaut "no path params / no REST verbs" rules in `.claude/rules/` do not apply to this codebase).

**Authorization invariants (read before the table).** Every `/manage/dresses/{dress_id}/...` route **resolves the parent dress first**: the first statement inside `tenant_session` — and, for presign, inside the advisory lock — is `dress = await dresses.by_id(session, tenant.id, dress_id)`; `if dress is None: raise CatalogNotFoundError`. `by_id` carries `tenant_id == tenant.id`, `id == dress_id` **and** `deleted_at IS NULL` (the `appointment_types.by_id` predicate verbatim), so an unknown id, an archived dress and another tenant's dress are one indistinguishable 404. `build_media_key(...)` is called only after that check returns a row, so no unverified id can reach an S3 key. Every media repository method takes `(session, tenant_id, dress_id, media_id)` and puts all three in the `WHERE` alongside `deleted_at IS NULL`: a media id that exists but belongs to a *different dress of the same tenant* is `404 NOT_FOUND`, never a silent re-parent. The reorder permutation is computed over `(tenant_id, dress_id, status='ready', deleted_at IS NULL)`.

**Transaction boundaries (invariant, stated once).** **No `MediaStorage` network method (`head_object`, `read_prefix`, `delete_object`) may ever be awaited inside a `tenant_session` block.** `tenant_session` is `async with session_factory() as session, session.begin()` — the whole block is one Postgres transaction, and boto3's default 60 s connect + 60 s read timeouts would pin a pool connection (and a per-dress advisory lock) across an S3 stall. `presigned_post` and `signed_get_url` may run anywhere: they are local HMAC. Mutations that return `DressDetailResponse` do their write transaction, then a short read transaction to build the view; signed URLs are minted after the session closes.

**Per-dress advisory locks.** Every write path touching `dress_media` for a dress — presign, confirm-promote, media delete, media reorder — takes `pg_advisory_xact_lock(hashtext('dress-media:' || :dress_id))` in its write transaction. The variants replace takes `pg_advisory_xact_lock(hashtext('dress-variants:' || :dress_id))`. Two distinct prefixes, so photo work and stock work on the same dress never serialise against each other, and both stay clear of F7's un-prefixed `hashtext(:tenant_id)` lock space.

**List query shape.** A page of `GET /manage/dresses` is exactly four statements: (1) the dress page `WHERE tenant_id = :t AND deleted_at IS [NOT] NULL [AND name ILIKE :q] ORDER BY sort_order, created_at DESC, id LIMIT/OFFSET`; (2) its `COUNT(*)`; (3) `SELECT dress_id, count(*) AS variant_count, coalesce(sum(quantity),0) AS total_quantity FROM dress_variants WHERE tenant_id = :t AND dress_id = ANY(:ids) AND deleted_at IS NULL GROUP BY dress_id`; (4) `SELECT DISTINCT ON (dress_id) *, count(*) OVER (PARTITION BY dress_id) AS media_count FROM dress_media WHERE tenant_id = :t AND dress_id = ANY(:ids) AND deleted_at IS NULL AND status = 'ready' ORDER BY dress_id, sort_order, id` for `cover` + `media_count`. Statements 3 and 4 are served by the leading columns of `idx_dress_variants_dress_active` and `idx_dress_media_dress_ready`. A dress with no matching group row gets `out_of_stock = true, total_quantity = 0, variant_count = 0, media_count = 0, cover = null` (edge case 6).

**Presign sequence.** (1) Throttle: `key = f"presign:{tenant_id}"`; `if limiter.is_blocked(key): raise MediaPresignThrottledError` → 429, before any work. (2) `tenant_session` #1, media advisory lock: resolve the dress (404); `SELECT` stale pendings (`status='pending' AND created_at < now() - pending_ttl`) capturing their `storage_key`s and soft-delete them; count ready + young-pending; `>= MAX_MEDIA_PER_DRESS` ⇒ `MediaLimitReachedError`; mint `media_id`, build the key, `insert_pending`. Commit. (3) **Outside any session**: `limiter.record_failure(key)` — `FixedWindowRateLimiter` counts **only what is explicitly recorded** (its docstring: "successes never count"), so a successful presign, which authorises a 10 MiB write to our bucket, must be recorded by hand. This is the `create_terms_version` precedent (`app/boutique/service.py:325`). Then best-effort `delete_object` for each swept key (the sweep is the only holder of those keys, so this is what bounds the orphan window to `PENDING_MEDIA_TTL_SECONDS` + the next presign for that dress rather than forever); then `presigned_post(...)`. A **rejected** presign records too: `CatalogNotFoundError` and `MediaLimitReachedError` are raised only after step (2) has opened a transaction and taken the per-dress media advisory lock, so leaving them unrecorded would make an unbounded loop against a full gallery — or against random dress ids — free. Schema/domain rejections do neither and are not recorded.

**Recording precedes signing (rev 2.2, corrected after the build).** The rev-2 prose ordered the throttle record *after* `presigned_post`, which leaves it unreachable when signing itself fails — and signing can fail: `S3MediaStorage.presigned_post` resolves credentials, so a rotated or expired IAM key raises while `is_configured` still returns `True` and the early guard passes. Two consequences, both real: the attempt never counts against the throttle, and the already-committed `pending` row occupies a gallery slot for the full hour. Twelve clicks would then answer `409 MEDIA_LIMIT_REACHED` — "gallery full" — on a dress with **zero** photos. So: record immediately after the transaction commits (the transaction is what the throttle bounds), and wrap `presigned_post` so `MediaNotConfiguredError` / `MediaStorageUnavailableError` **releases the just-minted row** under the media lock before re-raising, giving the owner a truthful 503 on the next attempt. Successes, rejections and signing failures all count.

**Confirm sequence.** (1) `tenant_session` #1: resolve dress and media row by `(tenant_id, dress_id, media_id)`; if already `ready`, build and return the detail view and stop — the idempotent short-circuit. (2) **Outside any session**: `head = await storage.head_object(key=row.storage_key)`; `None` ⇒ `MediaNotUploadedError`; `head.content_type != row.content_type` ⇒ best-effort `delete_object` then `MediaMismatchError`; `await storage.read_prefix(key=…, length=16)` must match `MAGIC_PREFIXES[row.content_type]`, else best-effort `delete_object` then `MediaMismatchError`. (An object that fails verification must not persist — that is the second half of the orphan story.) (3) `tenant_session` #2, media advisory lock: re-read the row and, **if still `pending`**, set `status='ready'` and `sort_order = coalesce(max(sort_order), -1) + 1` over this dress's ready rows; otherwise leave it. Build the detail view from the same transaction's rows. Confirm is idempotent **by construction** — it is an UPDATE of an existing row guarded by a `status = 'pending'` predicate plus the re-read inside the locked promote transaction. The `storage_key` unique index has nothing to do with it.

**Every mutation that changes a derived field returns the full detail view**, so the console never needs a follow-up GET. `DELETE /manage/dresses/{dress_id}` correctly stays `OkResponse` — the dress is gone.

**Note for F10 (media + stock).** `VariantResponse.quantity` is a **manage-only** field. 2. `app/catalog/` defines `CatalogNotFoundError(DomainNotFoundError)` and `CatalogValidationError(DomainValidationError)` — no new handler needed.
3. Without the first case, a boutique entering 60 dresses before filling any size matrix sees a full page of "אזל מהמלאי" on brand-new dresses. No API change — `variant_count` and `total_quantity` already carry it.

*Upload queue.* Each queued file renders a row with its file name, size (`<bdi>` LTR) and one of five states: `ממתין` · `מעלה…` · `מאמת…` (the confirm call) · `הועלתה` · `נכשלה — {reason}` + `נסי שוב`. **A byte-level progress percentage is explicitly out of scope**: `fetch` exposes no upload-progress event and F8 adds no XHR-based uploader or upload library, so `מעלה…` is an indeterminate indicator. Because uploads are sequential, exactly one row is ever non-terminal, and the queue plus a `role="status"` summary (`מעלה 3 מתוך 8`) is the progress affordance.

*Failure recovery.* On any failure — S3 non-2xx, network/CORS rejection, or a confirm error other than a transient 5xx — `MediaGallery` calls `api.deleteMedia(dressId, mediaId)` to **release the pending row** (which is why media DELETE accepts `pending` rows), then renders a Hebrew reason plus a `נסי שוב` button that re-runs the full presign → POST → confirm cycle for that file (a retry that has to re-upload always takes a fresh presign — the previous policy is dead once its 5-minute TTL elapses). The carve-out is the whole point of the carve-out: on `MEDIA_STORAGE_UNAVAILABLE` the pending row was **not** deleted, so the queue item keeps its `media_id` and `נסי שוב` re-issues the *confirm* alone — re-posting 9 MB over cellular for an object that already reached the bucket is exactly what "the pending row is left untouched and remains confirmable" exists to avoid. Before opening the picker the gallery blocks selecting more than `media_slots_remaining` files inline (`ניתן להעלות עד 12 תמונות לשמלה — נותרו 3`), so `MEDIA_LIMIT_REACHED` is only ever a race; when it does arrive the message is "הגלריה מלאה. ייתכן שהעלאות שנכשלו עדיין תופסות מקום — רענני את העמוד ונסי שוב." Without this path a few failed uploads on a flaky mobile uplink lock the gallery for an hour with no button that fixes it.

*Reorder accessibility.* ↑/↓ buttons, **no drag-and-drop in v1** (IS 5568 is a legal floor and drag is the least accessible reorder affordance). Each item's buttons carry an explicit `aria-label` (`הזזת תמונה 2 אחורה` / `הזזת תמונה 2 קדימה`); the first item's ↑ and the last item's ↓ are `disabled`; after the optimistic swap the component **restores focus to the same logical button** via a ref keyed by `media.id` — never let focus drop to `<body>`, which is what makes naive button reordering worse than drag. A single `role="status"` region under the gallery announces the result (`התמונה הועברה למקום 3 מתוך 5`) and also carries the upload-queue states. Reorder is optimistic with rollback on error, then a refetch on `MEDIA_ORDER_MISMATCH`.

*Signed-URL expiry.* Gallery `<img>` URLs expire after 15 minutes. A single `hasRefreshedRef` guard per gallery mount means the first `onError` from any image triggers exactly one `GET /manage/dresses/{id}` and subsequent errors are ignored; if an image still fails after that refresh it renders the no-photo placeholder rather than retrying. Gallery images take `alt={\`${dress.name} — תמונה ${index + 1}\`}`.

*Storage-disabled state.* When `media_uploads_enabled` is false (or any media call returns 503), the gallery renders a `role="status"` bordered notice — "העלאת תמונות עדיין לא זמינה" — with the file input `disabled` **and** the same explanation on its `<label>` (`disabled` alone removes the control from the tab order, so a screen-reader user would never learn why). The rest of the editor stays fully interactive. Nothing in the catalog tab becomes unusable because a bucket is missing.

## Edge cases

1. **Concurrent variant replaces** on the same dress → serialised by `pg_advisory_xact_lock(hashtext('dress-variants:' || dress_id))`; validation failures leave the previous matrix untouched. Two different dresses never contend, and a photo operation on the same dress never contends either (distinct lock prefix).
2. **Concurrent presigns racing the cap** → both run inside the same per-dress media advisory lock, so the 13th presign loses and gets `MEDIA_LIMIT_REACHED`, never an over-full gallery.
3. **Abandoned upload**: the presign succeeded, the browser died. The `pending` row stops counting toward the cap after 1 h and is swept on the next presign for that dress — and the sweep, which holds the row's `storage_key`, best-effort deletes the object too, so the orphan window is bounded rather than permanent. The UI's own failure path deletes the pending row immediately, so this is the abandoned-tab case, not the failed-upload case.
4. **Confirm without an upload** → `head_object` returns `None` → `409 MEDIA_NOT_UPLOADED`, row stays `pending` and expires normally. An S3 *outage* is a different answer: `503 MEDIA_STORAGE_UNAVAILABLE`, row untouched and still confirmable.
5. **Confirm retried after a lost response** → idempotent 200 with the same detail view: confirm is an UPDATE guarded by `status = 'pending'` plus a re-read inside the locked promote transaction, so a retry cannot double-bump `sort_order` and cannot fork a row.
6. **Dress with zero variants** → `out_of_stock = true`, `total_quantity = 0`, `variant_count = 0`. Correct per the derivation rule, and what a freshly created dress looks like — the manage UI shows "לא הוגדרו מידות", not "אזל מהמלאי".
7. **Archive then restore** → the archive UPDATEs carry `WHERE deleted_at IS NULL`, so a photo the owner deleted individually keeps its older stamp; restore reads the dress's `deleted_at` first and matches children on it. Photos and sizes deleted individually before the archive stay deleted. A restored dress rejoins the list with its ordering intact.
8. **Duplicate size by case/whitespace** (`" 38"`, `"US 6"` vs `"us 6"`) → normalised, then rejected by the `lower(size_label)` partial unique index as `409 DUPLICATE_SIZE`.
9. **Cross-tenant probes**: tenant A requesting B's `dress_id` or `media_id` — read, update, archive, restore, presign, confirm, delete, reorder — all return `404 NOT_FOUND`, indistinguishable from a missing row. **Within one tenant**, dress A's media id addressed through dress B's URL returns **404 for confirm and delete, and `409 MEDIA_ORDER_MISMATCH` for reorder** — reorder compares the payload against dress B's ready set before any per-media lookup, so an unknown id is a permutation conflict, per the API table's own rule for `PUT /media/order`. Either way the refusal is total: dress B never adopts dress A's photo. Every new repository method and endpoint gets an entry in the permanent isolation suite.
10. **Bucket not configured** → dress and variant CRUD fully usable, reads return `url: null`, only the media write endpoints answer `503 MEDIA_NOT_CONFIGURED`. The app boots normally and logs the fact (binding decision #5).
11. **Tampered upload**: the client edits the `key` or `Content-Type` form field, or posts a file of a different size than it declared → **S3** rejects it (403 / `EntityTooLarge` / `EntityTooSmall`), not us. Our DB row stays `pending` and the UI's failure path deletes it. This is the whole point of the POST policy.
12. **Content-type-honest polyglot**: an HTML/JS payload declared and posted as `image/jpeg` at exactly the declared size passes the policy → confirm's 16-byte magic-prefix check fails → the object is deleted and `409 MEDIA_MISMATCH` is returned. Even if it were stored, `attachment` disposition plus media-origin isolation keep it non-executable.
13. **Signed URL expiry during a long editing session** → the `<img>` `onError` path refetches the dress exactly once and re-renders with fresh URLs.
14. **Price null with `price_visible = true`** → valid; the storefront shows "מחיר בתיאום" (visibility is a permission, not a promise that a price exists). The editor's preview line makes this visible at write time.
15. **Repeat DELETE / repeat restore** → `404 NOT_FOUND` (the UPDATEs are predicated on `deleted_at IS NULL` / `IS NOT NULL`), matching F7's `archive_appointment_type`. The console disables the button while in flight and treats a 404 from archive/restore/delete as "already done" rather than surfacing an error toast.
16. **Bucket set, credentials missing** (the exact state F8 ships into) → `NoCredentialsError` maps to `503 MEDIA_NOT_CONFIGURED`, not a 500.

Assertions, with a real multipart POST from `httpx`:

| Assertion | Expected |
|---|---|
| happy path: presign → POST (fields then `file`) → `head_object` → `read_prefix` → confirm | 204 upload, object present, row `ready` |
| declared `image/jpeg`, posted `Content-Type: image/png` | **403** — policy rejects |
| declared 1 KiB, posted 1 MiB | **EntityTooLarge** — the exact `content-length-range` rejects |
| posted smaller than declared | **EntityTooSmall** — policy rejects |
| client rewrites the `key` field (own tenant prefix → another tenant's) | **403** — policy rejects |
| POST after expiry — signed directly via `S3MediaStorage` with `expires_in=1` + `time.sleep(1.5)` | **403** — policy rejects |
| signed GET fetches the object; the same URL after its TTL (`expires_in=1` + sleep) | 200 with `Content-Disposition: attachment`, then 403 |
| honest-size HTML payload declared `image/jpeg` → confirm | `MEDIA_MISMATCH`, object deleted |
| `delete_object` then `head_object` | `None` |

The two expiry rows use `expires_in=1` deliberately: they test S3's *enforcement* of the expiry field, not our default value — which is covered without network by the recording-fake assertions in `test_storage_port.py`. Sleeping 300 s and 900 s in CI is not an option.

## Risks & open items

1. **AWS account is `not-started`** (`external-applications.md` row 1 — the standing re-flag rule applies, and this spec re-flags it). F8 merges and is fully CI-green against MinIO; the staging/production bucket is then pure configuration. **The binding gate is F10, not F8.** F8 merges without the account; F10 cannot ship meaningfully without it, since every approved storefront screen is photography-led ("the grid IS the hero"). **Gate**: the AWS account must be `done` and the staging presign→upload→confirm→signed-GET smoke green **before F10's spec is written**, otherwise E2 closes on a monogram-only storefront that technically satisfies criterion 3 while being unshippable. Pilot-onboarding consequence: do not have the boutique enter catalog data before the bucket is live — dress and variant CRUD work, but the owner would have to revisit all ~60 dresses to add photos. Owner: user (only the user can file it). Trigger: now.
2. **F2 §B3 CORS — amended (done, 2026-07-24)**; `AllowedMethods` already reads `[POST, GET, HEAD]` with the F8 amendment note inline. **No further spec edit is needed** — a reviewer re-doing it risks a conflicting second edit. Two items remain: (a) §B3 must additionally record the **bucket-level SSE requirement** replacing F8's dropped form field — default encryption (SSE-S3) plus a bucket policy `Deny s3:PutObject` when `s3:x-amz-server-side-encryption` is absent; (b) verification — the first staging smoke after the bucket lands must run presign → browser-shaped POST → confirm → signed GET from a `https://*.<staging-domain>` origin and confirm the preflight passes. Until then every CORS assertion in this feature is server-side only: MinIO exercises the policy, not the browser preflight. Owner: F2 follow-up. Trigger: AWS account `done`.
3. **No image processing** — a 10 MiB original is served both to a bride on cellular *and* to the owner's own phone in the manage list, which is the heavier path in v1 (24 covers × up to 10 MiB). Mitigations in scope: the 10 MiB cap, `DRESS_LIST_DEFAULT_LIMIT = 24` with `loading="lazy"`, `SIGNED_GET_TTL_SECONDS` letting the browser cache within a session, **and the in-product upload guidance line in `MediaGallery`** — the epic's stated mitigation, now a shipped artifact rather than a document. A thumbnail/CDN feature is a known follow-up, bound by the media-origin-isolation invariant, and should be scheduled before onboarding boutique #2, not before the pilot.
4. **Orphan S3 objects — and the post-confirm rewrite window.** An S3 POST policy cannot be revoked, so a policy stays redeemable for the remainder of `PRESIGN_TTL_SECONDS` (300 s) even after confirm has head-checked the object, matched its magic bytes and promoted the row to `ready`. Within that window the same authenticated staff member of the same tenant can re-POST a different body — same key, same declared `Content-Type`, same exact byte count — over the object the gallery now points at, and the row stays `ready`. The magic-byte check therefore verifies the object **at confirm time**, not for its lifetime; the layers that cover the window are `signed_get_url` pinning `ResponseContentType` to the stored type plus `attachment` disposition, and the standing media-origin-isolation invariant. Neither is optional and neither may be trimmed on the strength of the magic-byte check alone. The only lever that shortens the window is `PRESIGN_TTL_SECONDS`, which cannot close it; it is judged immaterial because the actor must already be authenticated staff of that tenant, who can upload any accepted image anyway. Recorded here rather than fixed, and restated as a comment beside the check in `service.py`. Separately: a noncurrent-version lifecycle rule does **not** reach abandoned objects — an abandoned or failed-verification object is the *current* version of its key, and a current-version expiry rule on the media prefix would delete live gallery images, so it is not a safe substitute. F8 therefore reduces orphans structurally rather than reaping them: the stale-pending sweep deletes the objects it is about to orphan, confirm deletes the object it rejects, the UI's failure path deletes the pending row (and hence its object) immediately, and the exact `content-length-range` removes the deliberate large-orphan path. What remains is a failed `delete_object` after a committed soft-delete, logged at WARNING with `tenant_id`/`dress_id`/`media_id`/`storage_key` — that log line is the future reconcile job's input, so swallowing it silently is not acceptable. A `media-reconcile` CLI subcommand (list-prefix anti-join against `dress_media`, dry-run first) is **deferred**, not built here: it needs list-bucket IAM we do not have yet and a dry-run UX. Owner: E4 #21 infra runbook. Trigger: measurable orphan volume, or the first bucket cost review.
5. **`archived` growth** — soft-deleted dresses accumulate forever, as everywhere else in this codebase. The partial indexes keep the active paths clean; PPL erasure is a platform-wide job (checklist item), not F8's.
6. **F9 `manage-restyle.md` amendment required** — F8 adds a fifth console section "קטלוג" to a design that passed its gate against four (`profile | hours | types | terms`), and `manage-restyle.md`'s per-component table has no rows for `CatalogSection`, `DressEditor`, `VariantMatrix` or `MediaGallery`, nor a console-wide upload-queue or storage-disabled state. **Ruling (decided, not deferred): Catalog does NOT join `SetupProgress`** — setup means the configuration prerequisites for accepting bookings, catalog is ongoing content, and `storefront-catalog.md` already ships a dignified zero-dress state ("הקולקציה בדרך"), so the checklist stays 4-item and its denominators are unchanged. Still open: the console shell wireframe and its 768 tab-row note must be updated to five Hebrew tab labels and the 375 accordion re-checked, and the per-component table must gain the four new rows. Owner: F9 build. Trigger: amend `manage-restyle.md` in the same PR series as F8.
